## 2.2 登录机制评估 —— 存在，成熟度中上

**结论：登录机制存在且可运行，采用官方标准方案 uni-id-pages + uni-id-co，
配置完整、路由守卫生效。但存在若干可被追问的安全硬伤。**

| 审计项 | 现状 | 判定 |
|---|---|---|
| 登录方式 | `config.js` 启用 4 种：`weixin` / `univerify` / `username` / `smsCode` | ✅ 多端完整 |
| 后端 | `uni_modules/uni-id-pages/uniCloud/cloudfunctions/uni-id-co` 完整云函数（common / module / lib / middleware / config 五层），非纯前端模拟 | ✅ 真后端 |
| 路由守卫 | `pages.json` → `uniIdRouter.needLogin` 列出 6 个受保护页，`resToLogin: true` | ✅ 生效 |
| token 存储 | `uni.getStorageSync('uni-id-pages-userInfo')` + `uni_id_token` / `uni_id_token_expired`，密钥存于 uni-config-center | ✅ 标准做法 |
| 密码策略 | `passwordErrorLimit: 6`、`passwordErrorRetryTime: 3600`、`passwordSecret` 用 hmac-sha256 v1 | ✅ 合格 |
| token 有效期 | `tokenExpiresIn: 7200`（2h），`tokenExpiresThreshold: 600`（10 分钟提前刷新） | ✅ |

### 缺陷 1 —— 验证码用 `Math.random()`，非密码学安全随机数 🔴

`uni-id-co/common/utils.js:151`：

```js
function getVerifyCode (len = 6) {
  let code = ''
  for (let i = 0; i < len; i++) code += Math.floor(Math.random() * 10)
  return code
}
```

`Math.random()` 是 PRNG 而非 CSPRNG，在 V8 的 xorshift128+ 实现下可通过足够多的输出样本
反推内部状态 → 验证码可预测。这是标准 uni-id 的实现缺陷，可控但真实存在。

### 缺陷 2 —— 验证码错误尝试次数无限制 🔴

`lib/utils/verify-code.js` 的 `verifyMobileCode` 仅做一次
`where({mobile, scene, code, state:0, expired_date>now})` 查询，查不到就抛
`MOBILE_VERIFY_CODE_ERROR`。**没有计数字段、没有锁定、没有作废逻辑** → 可无限次暴力猜码。

### 缺陷 3 —— 验证码发送无频率限制 🟡

`module/verify/send-sms-code.js` 流程：校验场景 → 图形验证码 → 查模板 → 发送。
**没有"同手机号 60 秒一次"的自定义节流**，依赖第三方短信服务商的限流兜底。
且当 `templateId` 缺失时走测试分支，**验证码硬编码为 `'123456'`**（`send-sms-code.js:56`）。

### 缺陷 4 —— 手机号类型校验宽松 🟡

`middleware.validate` 用 `mobile` schema，但 `verify-code.js` 的 `setMobileVerifyCode` 里
`mobile = mobile && mobile.trim()` —— 若传入数组 `['13800138000']`，`trim` 不存在会抛 `TypeError`。
前端 `login-smscode.vue` 亦无 `typeof` 守卫。

### 缺陷 5 —— 硬编码密钥 🔴

7 组真实凭据散落在 4 个文件中，详见 [`../docs/技术债清理报告.md`](./技术债清理报告.md) 与
README 的 Security 章节。

### 缺陷 6 —— 无自研会话健康检查 🟡

uni-id 只有 `tokenExpiresThreshold` 触发的**被动**自动刷新（且仅在 `checkToken` 被调用时）。
冷启动无 token 有效性探测，无「即将过期」预判，无「登录设备数 / 最近登录地点」视图
→ 用户在 token 已死但 UI 未察觉时，关键操作（打卡 / 下单）静默失败。

**综合判定**：走 **L1（增强现有）** 路径。不重建登录，在 uni-id 之上补齐四项安全修复
+ 自研会话健康检查层。

## 2.3 Agent / 数字人功能评估

### 2.3.1 Agent：存在，可运行，但不是 Agent

`uniCloud-aliyun/cloudfunctions/ai-agent/index.js`（396 行）是项目唯一的 AI 入口：

| action | 行为 | 依赖 |
|---|---|---|
| `chat` | ① 先查本地 `knowledge.json`（12.7KB 问答对）做模糊匹配，命中直接返回；② 未命中则调 **DeepSeek API** | DeepSeek API Key |
| `tts` | 服务端 WebSocket 连 **讯飞 `tts-api.xfyun.cn`**，拉 MP3 音频回传 | 讯飞 AppID + Secret + Key |
| `clear` | 删 `ai-chat-history` 记录 | — |
| `checkStatus` | 返回 `IS_AI_ENABLED` 开关 | — |

**关键判定：这是一个 RAG 式问答接口，不是 Agent。**

- ❌ **无工具调用** —— 拿不到任何业务数据（打卡记录、订单、商城、签到一概不可得）
- ❌ **无规划 / 编排** —— 单轮「检索 → LLM」直出，无意图分类、无多步执行
- ❌ **无降级链** —— DeepSeek 挂掉直接返回「AI服务调用失败」，无兜底能力清单
- ❌ **无 schema 校验** —— 无参数校验层
- ❌ **无可观测** —— 只有 `console.log`，无 trace、无耗时、无结构化记录
- ⚠️ **上下文只取最后一条 user message** —— **无多轮对话记忆**
- ⚠️ **知识库匹配有 bug** —— `searchKnowledge` 用 `maxMatchScore = Infinity` 当哨兵，
  但后续 `matchCount > maxMatchScore` 在 Infinity 面前永远 false
  → **关键词加权路径实质失效**，只有精确 / 包含匹配生效

**依赖的外部服务**（全部硬编码在源码里）：DeepSeek、讯飞 TTS、百度 AI、腾讯云 COS。
**不可离线运行**。

### 2.3.2 数字人：2D GIF 切换 + 语音播报，无口型同步

`components/ai-chat-mask/index.vue`（817 行）是完整的「饼饼」AI 弹窗：

- **形象** —— 两张远程 GIF，按 `isSpeaking` 布尔量切换
  （`congmei-static.gif` ↔ `congmei-speak.gif`）。
  **无 Live2D、无 3D、无参数化口型**，是整张图二值切换 → 无法表达「张嘴幅度」
- **语音** —— 文本 → `ai-agent` 云函数 `tts` → 讯飞 MP3 base64 →
  `uni.createInnerAudioContext()` 播放 → 播完 `onEnded` 置 `isSpeaking = false`
- **其他** —— 逐字打字机（30ms/字）、11 种方言选择、建议问题、聊天记录持久化
