## 阶段 1 · 代码冻结与版本标记

### 1.1 版本号递增

编辑 `manifest.json`：

```json
{
  "versionName": "1.0.0",   // 面向用户展示的版本号
  "versionCode": "100"      // 面向应用商店的递增整数，每次发版必须增大
}
```

**递增规则**：

| 变更类型 | versionName | versionCode |
|---|---|---|
| 新功能 | 1.1.0 | 110 |
| 功能优化 | 1.0.1 | 101 |
| 缺陷修复 | 1.0.2 | 102 |

> `versionCode` 必须严格大于上一版，否则应用商店会拒绝上传。

### 1.2 跑通全量检查

```bash
npm run test:all
```

应全部通过：JSON 校验、auth-gateway、session-audit、Agent、Avatar。

### 1.3 提交并打 tag

```bash
git add -A
git commit -m "chore: release v1.0.0"
git tag -a v1.0.0 -m "跨境共生小程序 v1.0.0"
git push origin main
git push origin v1.0.0
```

推送 tag 会触发 `.github/workflows/build-apk.yml`（见阶段 3）。

### 1.4 注意事项

- 打 tag 前确认工作区干净：`git status` 应无输出
- tag 一旦推送难以撤回（虽然可以 `git tag -d` 删除，但已触发的流水线不会自动取消）
- 建议先在测试环境完整走一遍阶段 2–4，再打正式 tag

## 阶段 2 · 生产云空间部署

### 2.1 创建生产空间

**关键原则：生产空间必须与开发空间完全隔离。**

HBuilderX → 右键 `uniCloud-aliyun/` → 关联云服务空间 → 创建新空间（阿里云）。

> ⚠️ 本仓库的 `manifest.json` 中 `_spaceID` 指向的是**开发空间**。
> 切换到生产空间后该字段会被 HBuilderX 自动改写，**请勿提交这个改动**
> （`.gitignore` 已排除 `.hbuilderx/launch.json`，但 `manifest.json` 的
> `_spaceID` 仍会被跟踪 —— 如需隔离，请在提交前 checkout 该字段）。

### 2.2 上传数据库 Schema

右键 `uniCloud-aliyun/database/` → 上传所有 DB Schema。

会创建 13 张表：`uni-id-users`、`opendb-verify-codes`、`ai-chat-history`、
`user_photos`、`user_orders`、`userCheckedPlaces`、`quiz_questions`、
`shop_goods`、`init_food_data` 等。

### 2.3 上传云函数与公共模块

右键 `uniCloud-aliyun/cloudfunctions/` → 上传所有云函数、公共模块。

会部署 22 个云函数 + 1 个公共模块 `common/app-config`。

### 2.4 配置生产密钥

**这一步是生产环境与开发环境最大的差别，也是最容易被忽略的一步。**

#### 2.4.1 uni-id 账户体系

文件：`uni_modules/uni-config-center/uniCloud/cloudfunctions/common/uni-config-center/uni-id/config.json`

在 uniCloud 控制台（或直接修改本地文件后重新上传）配置：

```jsonc
{
  "tokenSecret": "<高强度随机串，至少 32 字符>",     // ⚠️ 必须替换
  "requestAuthSecret": "<高强度随机串，至少 32 字符>", // ⚠️ 必须替换
  "service": {
    "sms": {
      "smsKey": "<阿里云短信 AccessKey>",
      "smsSecret": "<阿里云短信 AccessSecret>",
      "scene": {
        "login-by-sms": { "templateId": "<真实模板 ID>" }
      }
    },
    "univerify": {
      "appid": "<uni-verify AppID>",
      "apiKey": "<uni-verify API Key>",
      "apiSecret": "<uni-verify API Secret>"
    }
  },
  "mp-weixin": {
    "oauth": {
      "weixin": {
        "appid": "<微信小程序 AppID>",
        "appsecret": "<微信小程序 AppSecret>"
      }
    }
  }
}
```

**生成高强度随机串**：

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

> 🔴 **务必替换 `tokenSecret` 与 `requestAuthSecret`。**
> 仓库中的占位符一旦被沿用到生产，任何人都能伪造登录 token。
> 这两项是本项目最敏感的凭据。

#### 2.4.2 第三方服务（按需，全默认关闭）

文件：`uni_modules/uni-config-center/uniCloud/cloudfunctions/common/uni-config-center/app-config/config.json`

```jsonc
{
  "deepseek": { "_enabled": true, "apiKey": "<你的 key>" },  // 不需要就保持 false
  "xfyun":   { "_enabled": true, "appId": "...", "apiSecret": "...", "apiKey": "..." },
  "baidu":   { "_enabled": true, "apiKey": "...", "secretKey": "..." },
  "cos":     { "_enabled": true, "bucket": "...", "secretId": "...", "secretKey": "..." }
}
```

**全部保持 `_enabled: false` 时，生产环境同样零外部调用、零费用。**

#### 2.4.3 开发模式开关

确保 `app-config` 的 `dev.simulateSms` 为 **`false`**：

```jsonc
{ "dev": { "simulateSms": false } }
```

> 🔴 **生产环境开启此开关会导致验证码不真实下发、直接返回给前端。**
> 这是最典型的"测试配置上生产"事故，务必逐项核对。

### 2.5 验证生产环境不返回 devCode

在生产空间中调用 `auth-gateway`：

```json
{ "action": "sendSmsCode", "mobile": "13800138000" }
```

检查响应：

- ✅ 生产环境：响应中**没有** `devCode` 字段，且短信实际送达
- ❌ 若出现 `devCode` → `dev.simulateSms` 未关闭，**立即修正**

## 阶段 3 · APK 打包与签名

### 3.1 证书准备

**方案 A · 使用 DCloud 公共测试证书（仅供演示，不可上架）**

HBuilderX → 发行 → 原生 App-云打包 → Android → 证书管理 → 使用公共测试证书。

> ⚠️ 公共测试证书**不适合正式上架**，也无法用于应用市场发布。
> 它的用途是让 APK 能装到手机上做演示。

**方案 B · 自建签名证书（可上架）**

```bash
# 生成 keystore（有效期 10000 天，妥善备份）
keytool -genkey -v -keystore cross-border-release.keystore \
  -alias cross-border -keyalg RSA -keysize 2048 -validity 10000
```

HBuilderX → 发行 → 原生 App-云打包 → Android → 证书管理 → 上传证书，
填写：
- 证书别名：`cross-border`
- 证书密码 / 私钥密码：创建时设置的值

> 🔴 **keystore 文件与密码必须离线备份。** 丢失后将无法为已上架应用发布更新。

### 3.2 HBuilderX 云打包

1. 菜单 → 发行 → 原生 App-云打包
2. 平台选择 **Android**
3. 应用版本：确认与 `manifest.json` 的 `versionName` 一致
4. 包名：`com.<你的组织>.crossborder`（**反向域名格式，一旦上架不可更改**）
5. 证书：选择 3.1 中配置的证书
6. 其他选项：
   - 权限：确认已按业务需求收敛（本项目已移除 5 项过度申请）
   - 第三方 SDK：按需勾选
7. 点击「打包」→ 等待云端构建 → 下载 APK

**产物位置**：`unpackage/release/` 目录。

### 3.3 GitHub Actions 自动打包

仓库已配置 `.github/workflows/build-apk.yml`，推送 `v*` tag 时触发。

**默认状态：不产出 APK。** 因为云打包需要 DCloud 授权凭据，
这些凭据不能入库。

启用方式（在仓库 Settings → Secrets 中添加）：

| Secret | 用途 |
|---|---|
| `HBUILDERX_USERNAME` | DCloud 账号 |
| `HBUILDERX_PASSWORD` | DCloud 密码 |
| `HBUILDERX_API_KEY` | 云打包 API Key |

配置后需在 workflow 的「构建 APK」步骤中接入实际打包命令
（当前为占位实现，见文件内注释）。

**自建 runner 方案**：在预装 HBuilderX CLI 的机器上注册 runner，
将 `runs-on` 改为你的 runner 标签，并在步骤中调用：

```bash
/opt/HBuilderX/cli publish --platform APP --project . -p android
```

### 3.4 产物归档

```bash
# 将 APK 复制到 dist/ 目录，供 GitHub Actions 归档
mkdir -p dist
cp unpackage/release/*.apk dist/
```

## 阶段 4 · 上线前检查清单

逐项打勾，任一不通过则**不要发布**。

### 4.1 凭据与配置

- [ ] 生产环境响应中**无 `devCode` 字段**（验证方法见 2.5）
- [ ] `tokenSecret` 已替换为随机串，**不是** `your-token-secret-placeholder`
- [ ] `requestAuthSecret` 已替换为随机串
- [ ] `service.sms.smsKey` / `smsSecret` / `templateId` 已配置为真实值
- [ ] `app-config` 中不需要的服务均为 `_enabled: false`
- [ ] `dev.simulateSms` 为 `false`
- [ ] 源码中无任何硬编码密钥（`npm run test:all` 会做扫描）

### 4.2 功能验证

- [ ] **验证码频率限制生效** —— 60 秒内第二次发送被拒绝（错误码 `auth-sms-too-frequent`）
- [ ] **验证码错误锁定生效** —— 连错 5 次后即使提交正确码也无法登录（`auth-code-locked`）
- [ ] **手机号异常入参被优雅拒绝** —— 传数组/数字/null 返回结构化错误，不崩溃
- [ ] **路由守卫生效** —— 未登录访问 `pages/choosedaka/*` 自动跳登录页
- [ ] **会话健康检查生效** —— 冷启动时 `session-audit` 返回 `valid: true`；
      token 过期后前端自动刷新或跳登录
- [ ] **Agent 降级正常** —— 问「今天天气怎么样」返回能力清单而非错误工具结果
- [ ] **数字人开口正常** —— 演示页点「让数字人说」，口型随节奏开合，点「停止」立即合嘴

### 4.3 构建与安装

- [ ] APK 在 **Android 10+ 真机**安装不闪退
- [ ] APK 在 Android 13+ 上能正确申请定位权限
- [ ] 首次启动无崩溃日志（`adb logcat`）
- [ ] 包名符合反向域名规范，且已确定不再变更
- [ ] 签名证书已离线备份

### 4.4 文档可复现性

- [ ] README 的 Getting Started 在**干净环境**（新 clone）可复现
- [ ] `npm run test:all` 全部通过
- [ ] `node scripts/check-workflow.js` 通过
- [ ] 演示账号说明清晰（脱敏占位符，非真实号码）

## 阶段 5 · 分发与反馈

### 5.1 GitHub Releases 分发

```bash
# 创建 tag 并推送（触发 Actions）
git tag -a v1.0.0 -m "跨境共生小程序 v1.0.0"
git push origin v1.0.0

# 在 GitHub 上创建 Release
gh release create v1.0.0 \
  --title "跨境共生小程序 v1.0.0" \
  --notes "见 README 的 Features 与 Known Issues 章节" \
  dist/*.apk
```

然后在 README 顶部添加 Releases 链接：

```markdown
[![Releases](https://img.shields.io/badge/Releases-v1.0.0-blue)](https://github.com/<你的用户名>/<仓库名>/releases)
```

### 5.2 分发渠道

| 渠道 | 适用 | 前置要求 |
|---|---|---|
| GitHub Releases | 简历附件、技术评审 | 无 |
| 直接安装 APK | 内部测试、体验 | 用户需开启「允许安装未知来源应用」 |
| 应用商店 | 正式发布 | 见 5.3 |

### 5.3 应用商店上架（列入 Future Work）

需要准备：

- **企业开发者账号** —— 个人账号在部分商店无法上架
- **隐私政策** —— 本项目使用定位、相机、相册、麦克风，必须逐项说明用途
- **软件著作权登记证书** —— 部分商店强制要求
- **应用截图与描述** —— 建议包含 Agent 演示页与数字人演示页
- **备案号** —— 国内商店要求 ICP 备案

> 隐私政策需特别说明：定位用于「打卡签到」，相机与相册用于「记录美食打卡照片」。

## 回滚方案

| 场景 | 操作 |
|---|---|
| 云函数更新后异常 | HBuilderX 右键云函数 → 重新上传上一版本代码 |
| 数据库 Schema 变更异常 | 控制台回滚 schema 版本 |
| APK 有严重缺陷 | 保留已发布版本，在 GitHub Releases 标记为 yanked，重新打包 |
| 密钥疑似泄露 | **立即在服务商控制台轮换密钥**，再重新上传对应云函数 |

> 🔴 密钥泄露的应急顺序是「先轮换，后查因」——
> 不要因为想查明原因而延迟轮换。
