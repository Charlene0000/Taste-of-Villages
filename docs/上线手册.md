## 阶段 1 · 代码冻结与版本标记

### 1.1 版本号递增

编辑 `manifest.json`：

```json
{
  "versionName": "1.0.0",   // 面向用户展示的版本号
  "versionCode": "100"      // 面向应用商店的递增整数，每次发版必须增大
}
```

**递增规则**：

| 变更类型 | versionName | versionCode |
|---|---|---|
| 新功能 | 1.1.0 | 110 |
| 功能优化 | 1.0.1 | 101 |
| 缺陷修复 | 1.0.2 | 102 |

> `versionCode` 必须严格大于上一版，否则应用商店会拒绝上传。

### 1.2 跑通全量检查

```bash
npm run test:all
```

应全部通过：JSON 校验、auth-gateway、session-audit、Agent、Avatar。

### 1.3 提交并打 tag

```bash
git add -A
git commit -m "chore: release v1.0.0"
git tag -a v1.0.0 -m "跨境共生小程序 v1.0.0"
git push origin main
git push origin v1.0.0
```

推送 tag 会触发 `.github/workflows/build-apk.yml`（见阶段 3）。

### 1.4 注意事项

- 打 tag 前确认工作区干净：`git status` 应无输出
- tag 一旦推送难以撤回（虽然可以 `git tag -d` 删除，但已触发的流水线不会自动取消）
- 建议先在测试环境完整走一遍阶段 2–4，再打正式 tag

## 阶段 2 · 后端部署

Sprint 5 后不再有云空间 —— 后端就是一个普通的 Node 进程。

### 2.1 准备环境变量

```bash
cd server
cp .env.example .env
# 编辑 .env，至少替换以下两项：
#   JWT_SECRET  ← 必须替换
#   DEV_MODE    ← 必须为 false
```

生成高强度随机串：

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

### 2.2 安装与初始化

```bash
npm ci --omit=dev
npx prisma generate
npx prisma db push
```

### 2.3 启动

```bash
# 开发
npm run dev

# 生产（PM2 示例）
pm2 start src/server.js --name cross-border-api
pm2 save && pm2 startup
```

### 2.4 反向代理与 HTTPS

Nginx 示例：

```nginx
server {
    listen 443 ssl;
    server_name api.your-domain.com;

    ssl_certificate     /etc/ssl/certs/api.crt;
    ssl_certificate_key /etc/ssl/private/api.key;

    client_max_body_size 10M;   # 允许上传照片

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

### 2.5 必须配置的生产环境变量

| 变量 | 状态 | 说明 |
|---|---|---|
| `JWT_SECRET` | 🔴 **必须替换** | JWT 签名密钥，不换则可伪造 token |
| `DEV_MODE` | 🔴 **必须 false** | 为 true 时验证码直接出现在响应里 |
| `CORS_ORIGIN` | 🟡 建议限定 | 生产建议写前端域名而非 `*` |
| `DATABASE_URL` | 🟡 按需 | 多实例部署时换共享数据库 |
| `UPLOAD_DIR` | 🟡 按需 | 生产建议挂持久卷 |
| `PORT` | 🟢 默认 3000 | — |

> 🔴 **`.env` 已被 .gitignore 排除**，绝不能提交。
> 部署时用环境变量注入（docker run -e / systemd EnvironmentFile / CI Secrets）。

### 2.6 验证生产环境不返回 devCode

```bash
curl -X POST https://api.your-domain.com/api/auth/send-code   -H "Content-Type: application/json"   -d '{"mobile":"13800138000"}'
```

响应中**不应出现** `devCode` 字段。若出现，说明 `DEV_MODE` 未关闭。

## 阶段 3 · APK 打包与签名

### 3.1 证书准备

**方案 A · 使用 DCloud 公共测试证书（仅供演示，不可上架）**

HBuilderX → 发行 → 原生 App-云打包 → Android → 证书管理 → 使用公共测试证书。

> ⚠️ 公共测试证书**不适合正式上架**，也无法用于应用市场发布。
> 它的用途是让 APK 能装到手机上做演示。

**方案 B · 自建签名证书（可上架）**

```bash
# 生成 keystore（有效期 10000 天，妥善备份）
keytool -genkey -v -keystore cross-border-release.keystore \
  -alias cross-border -keyalg RSA -keysize 2048 -validity 10000
```

HBuilderX → 发行 → 原生 App-云打包 → Android → 证书管理 → 上传证书，
填写：
- 证书别名：`cross-border`
- 证书密码 / 私钥密码：创建时设置的值

> 🔴 **keystore 文件与密码必须离线备份。** 丢失后将无法为已上架应用发布更新。

### 3.2 HBuilderX 云打包

1. 菜单 → 发行 → 原生 App-云打包
2. 平台选择 **Android**
3. 应用版本：确认与 `manifest.json` 的 `versionName` 一致
4. 包名：`com.<你的组织>.crossborder`（**反向域名格式，一旦上架不可更改**）
5. 证书：选择 3.1 中配置的证书
6. 其他选项：
   - 权限：确认已按业务需求收敛（本项目已移除 5 项过度申请）
   - 第三方 SDK：按需勾选
7. 点击「打包」→ 等待云端构建 → 下载 APK

**产物位置**：`unpackage/release/` 目录。

### 3.3 GitHub Actions 自动打包

仓库已配置 `.github/workflows/build-apk.yml`，推送 `v*` tag 时触发。

**默认状态：不产出 APK。** 因为云打包需要 DCloud 授权凭据，
这些凭据不能入库。

启用方式（在仓库 Settings → Secrets 中添加）：

| Secret | 用途 |
|---|---|
| `HBUILDERX_USERNAME` | DCloud 账号 |
| `HBUILDERX_PASSWORD` | DCloud 密码 |
| `HBUILDERX_API_KEY` | 云打包 API Key |

配置后需在 workflow 的「构建 APK」步骤中接入实际打包命令
（当前为占位实现，见文件内注释）。

**自建 runner 方案**：在预装 HBuilderX CLI 的机器上注册 runner，
将 `runs-on` 改为你的 runner 标签，并在步骤中调用：

```bash
/opt/HBuilderX/cli publish --platform APP --project . -p android
```

### 3.4 产物归档

```bash
# 将 APK 复制到 dist/ 目录，供 GitHub Actions 归档
mkdir -p dist
cp unpackage/release/*.apk dist/
```

## 阶段 4 · 上线前检查清单

逐项打勾，任一不通过则**不要发布**。

### 4.1 后端配置

- [ ] 生产响应中**无 `devCode` 字段**（验证方法见 2.6）
- [ ] `JWT_SECRET` 已替换为随机串，**不是** `please-change-me...`
- [ ] `DEV_MODE` 为 `false`
- [ ] `CORS_ORIGIN` 已限定为前端域名
- [ ] 数据库已初始化（`npx prisma db push`）
- [ ] 上传目录可写，且有持久化方案
- [ ] `server/.env` **未被提交**到 Git（\"server/.env\" 应有输出）

### 4.2 安全设计回归（Sprint 5 的核心验证项）

- [ ] 验证码 60 秒频控生效（`auth-sms-too-frequent` + `retryAfter`）
- [ ] 验证码连错 5 次作废（`auth-code-locked`）
- [ ] 手机号数组/数字/null 入参返回结构化错误，不崩溃
- [ ] JWT 鉴权生效（不带 token 返回 401，伪造 token 返回 401）
- [ ] 用户资料接口无法篡改 `loginCount` 等服务端字段

> 这五项可直接跑 `cd server && npm run test:api` 自动化验证（61 项）。

### 4.3 功能验证

- [ ] 登录 → 拿 token → 访问 profile 成功
- [ ] 路由守卫生效（未登录访问 `pages/choosedaka/*` 跳登录页）
- [ ] 会话健康检查返回 `valid: true`
- [ ] Agent 未知意图走降级（`source=fallback`），不返回错误工具结果
- [ ] 数字人开口正常，`stop()` 立即合嘴

### 4.4 构建与安装

- [ ] APK 在 Android 10+ 真机安装不闪退
- [ ] Android 13+ 正确申请定位权限
- [ ] 包名符合反向域名规范，且已确定不再变更
- [ ] 签名证书已离线备份
- [ ] 前端 `BASE_URL` 已改为生产域名

### 4.5 文档可复现

- [ ] README Getting Started 在**干净环境**（全新 clone，无任何配置）可复现
- [ ] `npm run test:all` 全部通过
- [ ] `cd server && npm run test:api` 全部通过（需后端已启动）
- [ ] `node scripts/check-workflow.js` 通过

## 阶段 5 · 分发与反馈

### 5.1 GitHub Releases 分发

```bash
# 创建 tag 并推送（触发 Actions）
git tag -a v1.0.0 -m "跨境共生小程序 v1.0.0"
git push origin v1.0.0

# 在 GitHub 上创建 Release
gh release create v1.0.0 \
  --title "跨境共生小程序 v1.0.0" \
  --notes "见 README 的 Features 与 Known Issues 章节" \
  dist/*.apk
```

然后在 README 顶部添加 Releases 链接：

```markdown
[![Releases](https://img.shields.io/badge/Releases-v1.0.0-blue)](https://github.com/<你的用户名>/<仓库名>/releases)
```

### 5.2 分发渠道

| 渠道 | 适用 | 前置要求 |
|---|---|---|
| GitHub Releases | 简历附件、技术评审 | 无 |
| 直接安装 APK | 内部测试、体验 | 用户需开启「允许安装未知来源应用」 |
| 应用商店 | 正式发布 | 见 5.3 |

### 5.3 应用商店上架（列入 Future Work）

需要准备：

- **企业开发者账号** —— 个人账号在部分商店无法上架
- **隐私政策** —— 本项目使用定位、相机、相册、麦克风，必须逐项说明用途
- **软件著作权登记证书** —— 部分商店强制要求
- **应用截图与描述** —— 建议包含 Agent 演示页与数字人演示页
- **备案号** —— 国内商店要求 ICP 备案

> 隐私政策需特别说明：定位用于「打卡签到」，相机与相册用于「记录美食打卡照片」。

## 回滚方案

| 场景 | 操作 |
|---|---|
| 云函数更新后异常 | HBuilderX 右键云函数 → 重新上传上一版本代码 |
| 数据库 Schema 变更异常 | 控制台回滚 schema 版本 |
| APK 有严重缺陷 | 保留已发布版本，在 GitHub Releases 标记为 yanked，重新打包 |
| 密钥疑似泄露 | **立即在服务商控制台轮换密钥**，再重新上传对应云函数 |

> 🔴 密钥泄露的应急顺序是「先轮换，后查因」——
> 不要因为想查明原因而延迟轮换。
